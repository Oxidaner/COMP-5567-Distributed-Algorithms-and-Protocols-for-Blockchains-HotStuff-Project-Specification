## 五人分工与交接

以下为五个**待认领席位**，姓名和学号由成员自己填入 `changes.md`。函数归属用于协调编辑，并不免除交叉审查与联调。

| 席位 | 主要实现与可核验证据 | 对接点 / 演示说明 |
| --- | --- | --- |
| 1：提案与换届 | `HotStuffDemo.propose()`、`next_view()`、`Node.enter_view()`；空块提案、Leader 轮换的测试与提交 | 和席位 2 约定投票事件；解释 Proposal、View。 |
| 2：安全投票与 QC | `HotStuffDemo.vote()`、`form_qc()`、`Node.extends()`、`can_vote()`；非法提案、单 View 一票、两票不成 QC 的测试与提交 | 和席位 3 约定 `dispatch_qc()` 的输入；解释 Vote、QC。 |
| 3：锁与提交 | `Node.receive_qc()`；HighQC、LockedQC、连续三链、祖先顺序的测试与提交；可选 A6 由其协调，席位 1 支援 timeout | 对接席位 5 的已提交区块列表；解释 Commit。 |
| 4：交易入口与选取 | `HotStuffDemo.submit()`、`select_transactions()`、`finalize_transactions()`；池、分叉重提和清理的测试与提交；可选 B5 | 对接席位 5 的回执；展示提交前余额、池和批量。 |
| 5：确定性执行 | `Node.execute_committed()`、`StateMachine.apply()`；执行顺序、余额不足、幂等回执的测试与提交；整合演示和结果；可选 B6 由其协调 | 对接席位 3 的提交顺序、席位 4 的清池；展示余额和失败回执。 |

每人还需对自己负责的功能写测试、记录实际提交和 AI 使用、审查另一人的 PR，并准备解释其函数。A7 若决定实现，由席位 2 主持并与席位 1/3 协作；B6 若决定实现，由席位 5 主持并与席位 4 协作。跨席位变更先在 PR 中标注受影响函数及对应审查人。

## 工作区流程

1. 每人从同步后的 `main` 建短名称个人分支，如 `proposal-view`、`safe-voting`、`commit-chain`、`transaction-pool`、`state-execution`；各自在独立 clone 或 Git worktree 中工作，同一分支只由一人推送。
2. PR 只改归属函数及必要的契约/测试，描述需求编号、行为、运行的测试、失败项、AI 辅助过的**具体函数**。共同文件按函数分片审查；合并前更新分支并解决冲突。
3. 先独立通过空块 A 测试，再处理 B 的隔离测试，最后跑集成测试。`tests/test_task_b.py` 的已提交历史 fixture 仅供隔离验证，生产执行必须由 A 的 commit 触发。
4. 每项合并后更新 `changes.md` 的实际人员、工作、证据、未完成项。由席位 5 协调一次真实运行的截图以外的**文本测试结果**和四分钟现场操作排练；各席位对自己负责的片段答疑。
